Auth · quarkus-auth-api

Issue, verify, renew, revoke — and the key that never leaves

Four endpoints, an RSA-signed JWT, and two rules that are easy to state and easy to get wrong: a token is only worth anything once its signature is checked, and a logout is only real if something other than the token remembers the session.

/auth/register · /auth/login · /auth/renew · /auth/logout · accounts in PostgreSQL · sessions and caches in Redis · smallrye-jwt verifies with the RSA public key
Why asymmetric keys here

Every service that has to accept a token needs the key that checks it, and only one needs the key that signs. With a shared secret, every verifier becomes a forger.

Why the access token is short

Statelessness means no lookup per call, and it also means an issued token cannot be recalled. The short window is not a preference — it is the only bound on how long a revocation takes to bite.

What Redis is doing here

Sessions and caches, which is what makes renew and logout possible at all. The token carries the claims; the session record is what says whether this one is still allowed.
